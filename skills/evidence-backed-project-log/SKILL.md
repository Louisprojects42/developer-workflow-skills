# Evidence Backed Project Log

Preserve a trustworthy project history without inventing past work. Read the existing log format and capture the base revision plus dirty state when Git is available. Do not create a new logging policy for unrelated work; use this workflow when requested or required by the project.

For the current change set, record its purpose, affected files, before/after behavior, assumptions, and actual verification results. Include documentation and evidence files themselves. Record the command, working directory, outcome, and exit code when observed. Distinguish a dry run from a live action and a syntax check from a behavioral or scientific result.

Link material claims to source, run records, raw outputs, or exact external references. Keep proposed, observed, supported-within-domain, and unresolved claims distinguishable. In a student portfolio, distinguish the learner's recorded reasoning from assistant drafting or external work; never infer understanding from a polished document.

Append corrections that reference earlier entries. Do not rewrite failed attempts as successful history. For unobserved changes, label reconstruction retrospective and leave the actor, date, or provenance unknown if there is no evidence. Never guess a future commit hash.

Hash stable external artifacts when that improves traceability. Avoid hashing a log inside itself; record hashes in a separate manifest or a later entry. Use relative paths for shareable evidence. Keep credentials and unrelated private material out of captured logs.

Deliver the updated log, an evidence index when needed, verification limits, and the next unresolved action. Publishing, committing, remote sync, and automation remain separate tasks unless already authorized.
